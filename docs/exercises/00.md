# Exercice 00 : exemple de départ

## Problèmes étudiés

Le projet 00 sert d'exemple résolu, hors du périmètre noté des exercices 01 à
10. Il permet de vérifier la traduction des nombres TypeScript en `float64`,
des appels de fonction, de l'addition et de `DEither.success`.

Deux défauts du socle ont été étudiés :

- **D1 — appel générique :** `EitherSuccessOf` est une fonction Go générique.
  Elle ne peut pas être stockée dans une variable avant que son paramètre de
  type soit déterminé.
- **D4 — ordre non déterministe :** transformer les arguments d'un appel et
  les instructions d'un bloc en parallèle peut faire varier l'ordre des
  transformations et des identifiants générés.

Sous Windows, le projet a aussi besoin d'une conversion entre les chemins
absolus DuploJS (par exemple `/C:/...`) et les chemins natifs demandés par
l'API TypeScript (par exemple `C:\...`).

## Stratégie

- À l'appel de `DEither.success`, récupérer le type de l'argument auprès du
  checker TypeScript, le traduire avec `typeTransformers`, puis construire une
  `InstantiationExpression` Go pour appeler directement
  `EitherSuccessOf[T](...)`. La fonction générique n'est donc jamais affectée
  à une variable non instanciée.
- Parcourir séquentiellement les arguments et les statements avec
  `DGenerator.asyncReduce` dans `shared/call.ts` et `statement/block.ts`.
  Chaque enfant est transformé dans l'ordre source; ses instructions `before`
  et son résultat sont ajoutés avant de traiter l'enfant suivant.
- Convertir les chemins uniquement aux frontières de l'API TypeScript, en
  conservant les chemins absolus DuploJS dans le reste du transpileur.

## Justification

L'AST Go contient déjà `InstantiationExpression`, qui représente l'appel
générique sans ajouter de syntaxe ni de mécanisme spécifique. Le type du
paramètre est choisi depuis le programme validé par TypeScript, plutôt que
d'être codé en dur pour `float64`.

Un parcours séquentiel préserve l'ordre d'évaluation JavaScript et rend
prévisible l'attribution des identifiants `Generated_N`. Il réutilise le
parcours asynchrone déjà employé par `transformSourceFile`.

## Go produit

L'appel à `DEither.success(one + two)` devient notamment :

```go
Generated_4 := Sourced_one
Generated_5 := Sourced_two
Generated_6 := Generated_4 + Generated_5
return shard_dependencies.EitherSuccessOf[float64](Generated_6)
```

Le type générique est explicitement instancié à partir du type vérifié de
l'argument. Les expressions sont évaluées en ordre, avant l'appel.

## Résultats observés

| Vérification | Résultat |
|---|---|
| `pnpm run build:00` | Réussie |
| `go vet ./...` dans `projects/00/dist` | Réussi |
| `go build ./...` dans `projects/00/dist` | Réussi |
| `go run .` dans `projects/00/dist` | Réussi |
| Comparaison de la sortie de référence TS et de Go | Identiques; les deux sont vides, car l'exercice n'affiche rien |
| Deux builds consécutifs | Manifeste SHA-256 des fichiers générés identique |
| `pnpm exec tsc -p tsconfig.app.json --noEmit` | Réussi |

Le script `pnpm test:types` n'a pas pu être lancé directement dans
PowerShell : son script `.sh` est appelé avec une syntaxe non reconnue par
Windows. Le contrôle TypeScript équivalent ci-dessus a passé. Le lint complet
n'a pas pu être validé : le script `.sh` n'est pas exécutable par le shell
Windows utilisé par pnpm. La configuration Oxlint exige Node.js `22.18.0` ou
plus récent (la machine utilise `22.16.0`); même avec un runtime temporaire
`22.18.0`, Oxlint échoue ensuite en essayant de lancer `tsgolint.js` comme un
exécutable Win32.

## Limites

- Le projet 00 ne teste pas le formatage de sortie de `DCommon.print`, car il
  ne produit aucune sortie.
- D2 (court-circuit de `&&` et `||`), D3, D5, D6 et D7 ne sont pas corrigés
  par cette fiche; ils restent à étudier dans les exercices concernés.
- Aucune mesure de performance ou de mémoire n'est présentée ici.

## Reproduire

Depuis la racine du dépôt :

```powershell
pnpm run build:00
pnpm exec tsx --tsconfig projects/00/tsconfig.json projects/00/index.ts
Push-Location projects\00\dist
go vet ./...
go build ./...
go run .
Pop-Location
```

Pour vérifier la reproductibilité, relancer `pnpm run build:00` et comparer
les chemins relatifs et les SHA-256 de tous les fichiers de
`projects/00/dist` entre les deux builds.
