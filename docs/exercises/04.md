# Exercice 04 : plusieurs chemins de retour

> Légende : **[observé]** = exécuté, la preuve est citée ; **[à vérifier]** = raisonnement ou attente non encore confirmés par une exécution.
> État : **04 ✅ identique à TypeScript** depuis le Sprint 3. Le constat d'avant le Sprint 2 était incomplet (C17, voir « Résultats observés »).

## Problèmes étudiés

Source : [`projects/04`](../../projects/04).

```ts
export function add(one: number, two: number) {   // type de retour NON annoté
	if (one === -1) {
		return DEither.fail();
	}
	return DEither.success(one + two);
}

const result = add(-1, 2);   // index.ts : même pipe que l'exercice 03
```

| # | Problème | Détail |
|---|---|---|
| P1 | **Plusieurs chemins de retour** | Un `return` dans le `if`, un autre après. Le type de retour est **inféré** par TypeScript : `Fail \| Success<number>`. |
| P2 | **Un type unique pour tous les retours** | En Go, une fonction a **un** type de retour : chaque `return` doit produire ce même type. |
| P3 | **Constructeur sans argument** | `fail()` n'a pas d'argument dont on pourrait tirer le paramètre de type : il faut le **type attendu** (le retour de la fonction). |
| P4 | **Nombre négatif** | `-1` est une `PrefixUnaryExpression` (opérateur `-` appliqué au littéral `1`), dans la condition et dans `add(-1, 2)`. |
| P5 | **Égalité stricte** | `===` sur des nombres. |

Sortie de référence **[observé]** (`add(-1, 2)` échoue, `isRight` est faux, le `pipe` renvoie le `Fail` inchangé) :
```
{
  '@duplojs/lang/kind/@DuplojsLangEither/left': null,
  '@duplojs/lang/kind/@DuplojsLangEither/information': 'fail',
  '@duplojs/lang/kind/@DuplojsLangEither/value': undefined,
  '@duplojs/lang/kind/@DuplojsLangEither/fail': null
}
```

## Variations considérées

| Variante | Ce qu'elle vérifie | Sortie de référence **[observé]** |
|---|---|---|
| `04-both-branches` | `return` dans le `if` **et** dans le `else`, sans `return` final (Go l'accepte comme instruction terminale) | `Fail` |
| `04-nested-if` | `return` dans un `if` imbriqué, retour inféré | `Fail` puis `Success(3)` |
| `04-unary` | `-x` sur une variable, `!` sur un booléen, `!==` | `Success(-3)`, `Fail`, `Fail` |

## Stratégie

| Problème | Traduction Go | Responsable | État |
|---|---|---|---|
| P1, P2 | Le type de retour Go vient du type **inféré** par le checker : `Fail \| Success<number>` donne `Either[float64]`. Tous les `return` ont ce type, et aucune conversion n'est nécessaire, puisque **toutes les variantes ont le même type Go** (ADR-1). | P4 | **Fait au Sprint 1** (types inférés par résolution de symbole, C11) |
| P3 | `fail()` donne `EitherFailOf[float64]()`, avec V tiré du **type attendu** : retour de la fonction englobante, même inféré. | P4 | **Fait au Sprint 1** (`either/expectedValueType.ts`) |
| P4 | `-1` (littéral) donne une constante `float64(-1)` ; `-x` (expression) donne un opérateur unaire Go ; `!b` donne `!b`. **Exception** : `-0` littéral donne `JSNegativeZero()`, parce qu'une constante Go ne peut pas valoir -0 (`float64(-0)` vaut +0, **[observé]** sur `01-print-values`). | P2 | **Fait** (Sprint 2, puis `-0` au Sprint 3) |
| P5 | `===` donne `==`, `!==` donne `!=` (déjà dans la table des opérateurs binaires). Pour les `float64`, `==` de Go se comporte comme `===` de JS, y compris `NaN != NaN` et `-0 == 0` (**[à vérifier]** par une variante). | – | Existant |
| `return` imbriqués | `if` dans le corps d'une fonction (Sprint 1, P2), avec un `return` dans la branche. | P2 | **[observé]** : `04-nested-if` passe déjà avec I1 |

## Justification

- **Pas de conversion aux `return`** : grâce à l'ADR-1, `Success<number>` et `Fail` ont **le même type Go** `Either[float64]`. Les `return` de différentes formes ne coûtent rien de plus qu'un retour de struct par valeur. C'est l'avantage de la représentation A sur une union générée ou une interface.
- **Type attendu plutôt que type de l'argument** pour instancier les constructeurs : c'est la seule source d'information pour `fail()`, et elle donne aussi un type cohérent pour `success(3)`, inféré en `Success<3>` (un littéral) mais traduit en `float64`.

## Go produit

**[observé]** `projects/04/dist/add.ts/add.ts.go` :

```go
func Sourced_add(Sourced_one float64, Sourced_two float64) (shard_dependencies.Either[float64]) {
	Generated_12 := Sourced_one
	Generated_13 := (float64)(-1)
	if Generated_12 == Generated_13 {
		return shard_dependencies.EitherFailOf[float64]()
	}
	Generated_14 := Sourced_one
	Generated_15 := Sourced_two
	Generated_16 := Generated_14 + Generated_15
	return shard_dependencies.EitherSuccessOf[float64](Generated_16)
}
```

- Le type de retour **inféré** `Fail | Success<number>` donne `Either[float64]`. Les deux `return` ont ce type, sans conversion (ADR-1).
- `fail()` est instancié en `EitherFailOf[float64]` d'après le type de retour de la fonction englobante.
- `index.ts` est identique à l'exercice 03 (même `func` literal dans le `pipe`).

## Limites

**[à vérifier]**
- `return;` **sans valeur** (D5) : non pris en charge à ce jour.
- Fonction dont **un chemin ne retourne rien** (le `return` final manque) : TypeScript inférerait `… | undefined`, ce qui n'est pas couvert.
- Retours de types Go **différents** selon le chemin (par exemple `Left<"a", string>` et `Success<number>`) : relève des replis A' et union fermée (ADR-1 et ADR-2), non implémentés.
