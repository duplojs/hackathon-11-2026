# Exercice 01 : union de retour, `const`, `if`, `isRight`, `print`

> Légende : **[observé]** = exécuté, la preuve est citée ; **[à vérifier]** = raisonnement ou attente non encore confirmés par une exécution.
> État : **01 ✅ identique à TypeScript avec le correctif d'intégration I1** (essayé sur `main` + patch, voir « Résultats observés »). Sur `main` après le merge du Sprint 1 (`4624394`), l'exercice **échoue encore**. Cette fiche documente les deux, car l'échec d'intégration est lui-même un résultat d'étude.

## Problèmes étudiés

Source : [`projects/01`](../../projects/01).

```ts
// add.ts
export function add(one: number, two: number): (
	| DEither.Success<number>
	| DEither.Fail
) {
	return DEither.success(one + two);
}

// index.ts
const result = add(1, 2);

if (DEither.isRight(result)) {
	DCommon.print(result);
```

## Stratégie

Choix effectivement implémentés au Sprint 1 (PR #6, #7 et #8), d'après le code mergé, les notes de P4 et les messages de commit de P3. Les PR #6 à #8 n'ont **pas** de description.

| Problème | Traduction Go | Où | Détail |
|---|---|---|---|
| P1 type | `( Success<number> \| Fail )` donne **`shard_dependencies.Either[float64]`** | `type/parenthesized.ts`, `duplojs/either/index.ts` et `either/types/` (P4) | Les parenthèses sont déballées. Chaque membre de l'union est reconnu **par symbole** (`resolveReferenceModule` vers `@duplojs/lang` `dist/either/`), et les types de valeur sont regroupés **par rendu Go** : un seul type V donne `Either[V]` ; `Fail` seul donne `Either[JSUndefined]` ; des types différents donnent `notSupport` (A', ex. 09). |
| P1 valeur | `success(x)` donne `EitherSuccessOf[V](x)` ; `fail()` donne `EitherFailOf[V]()` | `either/success/`, `either/fail/`, `either/expectedValueType.ts` (P4) | Instanciation **explicite** (D1). V est tiré du **type attendu** : type contextuel, puis retour de la fonction englobante (même inféré), puis type propre de l'appel. Sans ça, `fail()`, qui n'a pas d'argument, ne pourrait pas être instancié. |
| P2 premier niveau | `var Sourced_result Either[float64]` (package) et `Sourced_result = …` dans `init()` | `statement/variable.ts` (P2) | Type tiré du checker (`getTypeAtLocation`, puis type de base du littéral, puis `typeToTypeNode`, puis `typeTransformers`). |
| P2 dans une fonction | `x := …` | `statement/variable.ts` (P2) | `const` et `let` acceptés ; une seule déclaration par instruction, et un identifiant simple (sinon `context.error`). |
| P3 | `if cond { … } else { … }` | `statement/if.ts` (P2) | Les `before` de la condition sont placés avant le `if`. Ceux d'un `else if` vont **dans** le `else` (variante `01-else-if`, voir Limites). |
| P4 | `isRight(e)` donne `e.IsRight()` ; `isLeft(e)` donne `e.IsLeft()` | `either/isRight/` (P3) | Le handler ne connaît pas la représentation : il appelle une méthode du contrat, inlinée par Go. **Non branché dans le routeur sur `main`** (D10). |
| P5 | `print(v)` donne `shard_dependencies.Print[T](v)` | `duplojs/common/print/` et `sharedDependency/defaults/inspect.ts` (P3) | Formateur `util.inspect` (règle `reduceToSingleString`, `breakLength` 80, calibrée sur Node). `print(x)` étant une instruction isolée, le routeur ne reçoit que `DCommon.print` : le handler remonte à l'appel via `node.parent` pour lire T. |

### Go produit **[observé]** (`main` `4624394` + correctif I1)

> Les noms de packages `Sourced_…` encodent le **chemin absolu** du fichier source (défaut D8). Ils sont abrégés ici en `Sourced_<add.ts>`.

`add.ts.go` :
```go
func Sourced_add(Sourced_one float64, Sourced_two float64) (shard_dependencies.Either[float64]) {
	Generated_6 := Sourced_one                // chaque opérande est évalué dans l'ordre
	Generated_7 := Sourced_two
	Generated_8 := Generated_6 + Generated_7
	return shard_dependencies.EitherSuccessOf[float64](Generated_8) // instanciation explicite (D1)
}
```

`index.ts.go` :
```go
var Sourced_result shard_dependencies.Either[float64] // const de module : variable de package

func init() {                                           // code de premier niveau : init() du package
	Generated_1 := Sourced_<add.ts>.Sourced_add
	Generated_2 := (float64)(1)
	Generated_3 := (float64)(2)
	Sourced_result = Generated_1(Generated_2, Generated_3)
	if Sourced_result.IsRight() {                       // DEither.isRight
		Generated_4 := shard_dependencies.Print[shard_dependencies.Either[float64]] // Print instancié
		Generated_5 := Sourced_result
		Generated_4(Generated_5)
	}
}
```

`shard_dependencies.go` (283 lignes, extrait des signatures) :
```go
type EitherKind uint8                     // Right = 0, Left = 1, Success = 2, Fail = 3
type Either[V any,] struct { Kind EitherKind; Information string; Value V }
func EitherSuccessOf[V any,](value V) (Either[V])
func EitherFailOf[V any,]() (Either[V])
func (e Either[V]) IsRight() (bool)       // Kind == Right || Kind == Success
func (e Either[V]) IsLeft() (bool)        // Kind == Left  || Kind == Fail
func (e Either[V]) InspectEntries() ([]InspectEntry) // clés DuploJS dans l'ordre de print
type InspectEntry struct { Key string; Value any }
type Inspectable interface { InspectEntries() []InspectEntry }
func JSNumberToString(value float64) (string)
func Print[T any,](value T) (T)
```

`go build -gcflags=-m` **[observé]** : `Sourced_add`, `EitherSuccessOf`, `IsRight` et `IsLeft` sont **inlinés** (« can inline » et « inlining call »). Les **seules** allocations signalées sont sur le chemin d'affichage :
```
shard_dependencies.go:215:26: []shard_dependencies.InspectEntry{...} escapes to heap
shard_dependencies.go:218:13: shard_dependencies.JSNull{} escapes to heap
```
Le calcul (`add`, `isRight`) n'alloue rien, ce qui confirme que le `any` est confiné à `print`.

## Justification

- **Représentation des Either (ADR-1)** **[observé]** dans [ADR-1](../decisions/ADR-1-either.md) §3 et §4 : le struct par valeur `Either[V]` ne fait **aucune allocation**, alors que l'interface (option B) et `Value any` (option C) allouent à chaque retour non inliné. Il est **5 à 8 fois plus rapide** sur 1000 valeurs (`Map1000` : environ 20 µs contre 150 à 164 µs ; 32 Ko contre 57 à 80 Ko). Un seul type Go couvre `Success<T>`, `Fail` et leurs unions : aucune conversion n'est nécessaire au `return` dans l'exercice 01.
- **`Kind` à 4 valeurs plutôt qu'un booléen :** `print` doit distinguer `success`/`right` et `fail`/`left`, puisque les clés affichées diffèrent. Un `uint8` ne coûte rien de plus qu'un `bool` dans le struct.
- **Variable de package plutôt que `:=` au premier niveau :**
  1. Une `const` de module TypeScript est visible des fonctions du fichier (variante `01-const-used-by-function`) ; une variable locale à `init()` ne le serait pas.
  2. Une variable de package inutilisée n'est **pas** une erreur en Go, contrairement à une variable locale (défaut D6).
  3. Le code de premier niveau reste dans `init()` : l'ordre d'exécution des modules est conservé, puisque Go initialise les packages importés avant le package importateur.
- **`any` limité à l'affichage :** `InspectEntry.Value any` sert uniquement au chemin de `print`, qui est limité par les entrées-sorties. Les calculs (`add`, `isRight`) n'utilisent jamais `any`. **[à vérifier]** : mesurer le coût de `print` n'apporterait rien au comportement, et ce n'est pas prévu.
- **Reconnaissance par symbole :** `isRight` et `print` sont identifiés en résolvant le symbole jusqu'à `@duplojs/lang` (`dist/either/`, `dist/common/`), jamais par leur nom. La variante `01-alias` le vérifie.

## Limites

**[observé]**
- **Types chaîne, booléen et tableau absents** (D12) : `print("succès")` et `print([1, 2, 3])` ne se transpilent pas. Cela bloque 5 variantes, et c'est prévu au Sprint 2 (P4).
- **Union hétérogène** (types de valeur différents selon le côté, par exemple `group` de l'ex. 09) : `notSupport` ; la représentation A' est prévue à l'ex. 09.
- **`print` avec un 2e argument** (`"warn"`, `{ depth }`, `{ columns }`) : `context.error` explicite.
- **`print` passé en valeur** (non appelé) : renvoie `Print` **non instancié**, ce qui est le même piège que D1. Le cas n'apparaît dans aucun exercice, et il relève de l'ADR-3.
- **`success` / `fail` passés en valeur** : `fail` donne `notSupport`, `success` garde un comportement non instancié (ADR-3).
- **`var` JS, plusieurs déclarations par instruction** (`const a = 1, b = 2`) **et déstructuration** : `context.error` explicite.
- **Noms de packages en chemin absolu** (D8) : le Go produit dépend de la machine, ou même du dossier de la copie de travail, et il est peu lisible.

**[à vérifier]**
- **Alias de type local** (`type R = Success<number> | Fail`) : la référence se résout vers l'alias et non vers DuploJS, donc ce n'est pas pris en charge (note de P4).
- **`Left<"x">` sans valeur** (`Left<"x", undefined>`) : pas de transformer pour `undefined` ; à traiter avec l'ex. 06 si besoin.
- **`else if` avec un appel dans la condition** : la variante `01-else-if` est écrite pour le vérifier (l'appel ne doit avoir lieu que si la condition précédente est fausse), mais elle bloque encore sur les types chaîne.
- **Formes de `util.inspect` non couvertes** : objets imbriqués au-delà de la profondeur 2, `Map`/`Set`, tableaux de plus de 6 éléments sur plusieurs lignes, chaînes contenant des `'`. La règle une ligne / plusieurs lignes est calibrée empiriquement sur Node (P3).
- **`Fail` seul** donne `Either[JSUndefined]` : le cas n'est pas couvert par une variante dédiée.
